# 후보 수집 수정과 보류 문항 비교

## 결론

**조기 탐색 종료는 수정했고, 후보 근거 회수도 늘었지만, 아직 유료 Jev 평가나 기본 활성화를 정당화할 수준은 아닙니다.** 로컬 최종 반환의 근거 보존은 여전히 낮고, 일부 문항은 악화됐으며 탐색 비용도 늘었습니다. 변경은 커밋·푸시하지 않은 실험 패치로 남겼습니다.

## 무엇을 바꿨나

- 후보가 처음 12개 생겼다고 탐색을 끝내지 않습니다. 기존 파일·항목·바이트·시간 한도 안에서 계속 읽고, 최대 12개인 후보 풀을 갱신합니다.
- 반복 빈도보다 서로 다른 질의어의 일치를 사용합니다. 정확한 단어·camel-case 식별자 부분을 우연한 부분 문자열보다 높게 평가하고 파일명 일치를 반영합니다. 동점이면 짧은 인용, 경로, 줄 순서로 정합니다.
- 영어 기능어 잡음을 줄이고, 긴 병합 창을 자를 때 더 많은 질의어가 일치하는 줄을 중심으로 잡습니다. 원문과 줄 번호는 바꾸지 않습니다.
- 파일·시간·전송량 등 `LIMITS`, 자격 증명 필터, 세션 승인, 취소, 렌더러, 공급자 처리와 기존 도구는 유지했습니다. 자격 증명 가림 표시 오탐도 이번에 우회하지 않았습니다.

관련 제품 파일은 `extensions/pi-jev-context/core.mjs`입니다. 새 동작의 회귀 검사 7개를 추가했고, Pi 통합 검사의 반올림 응답 검증은 고정 파일명이 아닌 실제 입력 순서의 역전을 확인하도록 바꿨습니다.

## 비교 설계

이전 10문항은 개발 세트로 전환했습니다. 별도 공개 저장소 `pi-ask-user`에서 새 4문항과 정답 근거를 코드 변경 전 **08:57:47 UTC**에 동결했습니다. 독립 근거 조사 후 부모가 줄 범위와 의미를 검증했습니다. 이는 한 생태계 안의 작은 제3 저장소 검사이지 블라인드·대표 표본은 아닙니다.

코드와 비교기를 **09:09:24 UTC**에 동결한 뒤, 동일한 검증된 소스 복사본에 기존/수정 구현을 교대로 실행했습니다. 총 **168회**(14문항 × 2언어 × 2구현 × 3반복)이며 모든 조건에서 반복 간 후보·반환·coverage가 일치했습니다. 보류 결과를 보고 점수를 다시 조정하지 않았습니다.

## 영어 직역 질의 결과

| 세트 | 후보에 들어온 필수 근거 | 로컬 최종 반환의 필수 근거 | 후보에 모든 근거가 있는 문항 | 최종 반환에 모든 근거가 있는 문항 |
|---|---:|---:|---:|---:|
| 개발 10문항 · 기존 | 3/34 | 0/34 | 0/10 | 0/10 |
| 개발 10문항 · 수정 | 6/34 | 2/34 | 0/10 | 0/10 |
| 보류 4문항 · 기존 | 2/9 | 0/9 | 1/4 | 0/4 |
| 보류 4문항 · 수정 | 4/9 | 1/9 | 2/4 | 0/4 |

문항별 재현율 평균으로 보면 개발 후보는 **9.17%→18.33%**, 보류 후보는 **33.33%→58.33%**입니다. 표의 근거 개수 비율과 문항 평균은 분모가 다릅니다.

- 새 보류 문항 `h1`(시간초과 동작)은 후보 재현율 **0→1**, 최종 반환 **0→0.5**로 개선됐습니다.
- `h2`(다중 선택 반환 순서)는 후보에는 계속 필요한 근거가 있지만 최종 반환에는 남지 않았습니다.
- **`h3`(좁은 레이아웃)은 후보 재현율 1/3→0으로 악화됐습니다.** 개발 세트의 `s1`, `s4`도 이전에 찾던 일부 근거를 잃었습니다. 평균 개선만으로 이를 숨기지 않습니다.
- 정답을 아는 최적 정렬의 문항 평균 상한도 수정 구현에서 개발 **18.33%**, 보류 **58.33%**에 그쳤습니다. 이는 Jev 측정치가 아닙니다.

한국어 원문은 개발·보류 양쪽에서 여전히 후보/반환 근거가 **0개**입니다. 이번 변경은 번역이나 의미 검색을 추가하지 않았습니다. 실제 부모 모델이 영어 질의와 더 좁은 경로를 만들 수 있으므로, 이를 실제 한국어 사용자 작업 정답률로 해석하면 안 됩니다.

## 비용과 남은 병목

영어 scan/render 중앙값은 개발 세트 **6.3→109.7ms**, 보류 세트 **7.1→18.9ms**였습니다. 더 넓게 읽는 비용이 생겼으며 속도 개선으로 주장하지 않습니다. 이는 warm-cache 로컬 단계만의 시간으로, 주 모델·승인·인증·네트워크·전체 작업 시간을 포함하지 않습니다.

개발 세트에서 읽은 파일은 기존 4~7개에서 수정 후 72~79개로 늘었습니다. 하지만 키워드가 많은 기존 벤치마크 프롬프트·변경 기록·문서·테스트가 실제 구현보다 앞서는 경우가 남습니다. 키워드만으로 권위 있는 구현 근거를 판별하지 못하며, 단일 파일의 후보 과점도 막지 않습니다. 기존 보안 필터가 `runtime.ts`의 가림 표시를 자격 증명처럼 판단하는 오탐도 남았습니다.

영어 14문항 모두 두 구현에서 요청 직렬화 검사를 통과했지만, **실제 Jev 요청은 0회**입니다. 정렬이 적용되면 좋아질 수 있다는 상한과 실제 모델의 개선 효과는 구분했습니다.

## 판단과 다음 단계

- 이 패치를 완료된 품질 개선이나 배포 준비 상태로 취급하지 않습니다. 기존 설치와 기본 도구 구성은 바꾸지 않았습니다.
- 다음에는 정적 규칙을 더 붙이기보다, 독립 세션에서 부모가 실제로 만드는 `paths`/`goal`과 후속 읽기를 관찰하는 작은 A/B를 먼저 설계하는 편이 타당합니다. 현재처럼 넓은 경로와 문장형 질의를 강제로 주는 조건과 실제 사용의 차이를 확인해야 합니다.
- 추가 모델 실행과 Jev 실호출은 공급자·모델·데이터 범위·최대 호출 수·최대 비용을 정하고 별도 승인받아야 합니다.
- 다시 조정할 경우 현재 보류 4문항도 개발 자료가 됩니다. 같은 문항을 재사용하면서 보류 성능이라고 주장하지 않습니다.

정답률, 자연스러운 도구 선택, 후속 검색·읽기 횟수, 전체 시간·비용은 미측정입니다. 정답 근거는 사전 지정한 구현 줄 범위이며, 다른 유효한 근거를 과소평가할 수 있습니다.

## 검증·산출물

- `heldout-tasks.json`, `heldout-gold.json`, `heldout-manifest.json`, `heldout-freeze.json`: 코드 변경 전 확정한 보류 자료.
- `comparison-freeze.json`, `compare.mjs`, `compare.test.mjs`, `results.json`: 코드 동결·비교기·집계 회귀·모든 결과.
- 기존 파일럿 데이터·평가기·결과는 그대로 보존했습니다. 재현 방법은 `README.md`에 있습니다.
- 최종 `npm run check` 통과: Node 테스트 **118개**, 격리된 Pi 0.85.0 타입/로딩·모의 통합 검사, Python 테스트 **5개**와 스킬 검사. 별도 평가기 테스트 **9개**도 통과했습니다. `git diff --check`와 동결 해시·점수·출력 한도 검증을 통과했습니다.
- 원격 CI는 커밋·푸시하지 않았으므로 실행하지 않았습니다. 평가용으로 만든 임시 공개 소스 복사본만 정리하고, 원래 사용자 작업과 기존 파일럿 결과는 보존했습니다.
