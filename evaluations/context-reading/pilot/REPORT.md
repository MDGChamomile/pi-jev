# 로컬 후보 탐색 파일럿 결과

## 결론

**이번 넓은 디렉터리 범위·고정 질의 조건에서는 Jev 유료 평가보다 로컬 후보 탐색의 병목을 먼저 다루는 편이 타당합니다.** 영어 번역 질의에서도 필수 구현 근거 34개 중 3개만 후보에 들어갔고, 실제 로컬 반환에는 하나도 남지 않았습니다. 이 후보 그대로라면 완벽한 정렬도 필요한 근거 대부분을 복구할 수 없습니다.

이는 **실제 에이전트의 정답률이 0이라는 뜻이 아닙니다.** 주 모델이 범위를 좁히거나 더 나은 검색어를 만들 때의 효과, 일반 `read`/검색을 사용하는 기준선, 자연스러운 도구 선택은 아직 측정하지 않았습니다. 미리 지정한 구현 근거만 채점했으므로 문서나 다른 유효한 코드 근거를 과소평가할 가능성도 있습니다.

## 실행 범위

- 공개 저장소 두 개의 커밋·Git 트리를 GitHub 메타데이터와 대조하고, 작업 디렉터리가 아닌 `git archive`로 376개 파일을 추출했습니다. 자세한 핀과 해시는 `tasks.json`, `corpus-manifest.json`에 있습니다.
- 질문 14개를 먼저 작성했습니다. 구현 근거를 확정한 10개를 채점했습니다. 위치가 알려진 읽기 요청 2개는 향후 도구 선택 대조군으로 남겼습니다. 실행 파일의 의미가 모호한 `b2`, 외부 네이티브 백엔드 검증이 필요한 `b5`는 미해결 상태를 명시하고 제외했습니다.
- 독립 근거 조사 1회는 도구 예산 제한으로 부분 완료되었습니다. 부모가 결정적인 소스 범위를 확인하고 잘못된 줄 번호·긴 인용을 고쳤습니다. `s5`는 재시도를 Pi에 위임한다는 불확실성 경계를 정답에 명시했습니다. `b2`/`b5`는 억지로 정답을 만들지 않았습니다.
- 질문·영어 번역·정답·코퍼스·리더·평가기 해시를 **2026-09-28 08:40:17 UTC**, 검색 전에 동결했습니다. 결과는 08:40:24 UTC에 생성됐습니다.
- 한국어 원문/사전 작성 영어 직역 × 두 파일 생성 순서 × 3회 반복 × 10문항 = **120회 로컬 scan/render**입니다. 이후 정답 파일 경로를 준 진단 10회를 별도로 실행했습니다.
- **실제 Jev HTTP 요청 0회.** 인증, 활성 Pi 설치, 기본 도구 변경, 제품 코드 수정, Git 커밋·푸시는 하지 않았습니다.

## 주요 결과

두 파일 생성 순서에서 점수는 같았습니다. 그러나 실제 파일시스템 탐색 순서도 동일했습니다(하위 조사 162개 항목, 브라우저 108개 항목). 따라서 **서로 다른 탐색 순서에 견고하다고 입증한 실험은 아닙니다.** 각 조건의 세 반복에서도 후보·반환·coverage는 동일했습니다.

| 고정 질의 | 후보의 필수 근거 | 로컬 최종 반환의 필수 근거 | 정답을 아는 최적 정렬의 반환 상한 | 모든 필수 근거를 후보에 포함한 문항 |
|---|---:|---:|---:|---:|
| 한국어 원문 | 0/34 | 0/34 | 0/34 | 0/10 |
| 영어 직역 | 3/34 | 0/34 | 3/34 | 0/10 |

영어의 문항별 재현율 평균은 후보 **9.17%**, 로컬 반환 **0%**, 최적 정렬 상한 **9.17%**입니다. 근거가 일부라도 들어온 문항은 `s1`(4개 중 1개)과 `s4`(3개 중 2개)뿐입니다. 전체 근거 기준 비율 3/34와 문항 평균 9.17%는 분모가 다릅니다.

영어에서는 10문항 모두 요청 직렬화가 가능했지만, **보낼 수 있는 요청과 유용한 후보가 있는 요청은 다릅니다.** 이를 실제 API 성공이나 Jev 품질로 세지 않았습니다.

## 관찰된 병목

### 1. 첫 12개 후보가 나오면 탐색 자체가 끝납니다

`extensions/pi-jev-context/core.mjs:174`는 후보 수가 12개가 되면 `stopScan = true`로 설정합니다. 이번 영어 조건은 **4~7개 파일만 읽고** 모두 그 한도에 도달했습니다. 초기 테스트 파일·설정 코드·공통 작업 코드에서 후보가 채워져 이후 구현 파일까지 충분히 가지 못했습니다.

이는 전체 허용 범위를 탐색한 뒤 좋은 12개를 고르는 동작과 다릅니다. 개선을 검토한다면 기존 파일·바이트·시간 한도는 유지하면서, 그 한도 안에서 더 넓게 훑고 후보를 선택하는 방식이 우선입니다. 이 보고서에서는 변경하지 않았습니다.

### 2. 한국어 문장을 그대로 넣으면 영어 코드와 어휘가 맞지 않았습니다

현재 `terms()`와 줄 검색은 토큰의 부분 문자열 일치입니다. 한국어 조건은 72~79개 파일을 읽었지만 후보가 0개였습니다. 번역·의미 검색은 수행하지 않습니다. 다만 실제 부모 모델이 영어 검색어를 만들 수도 있으므로, 이것만으로 한국어 사용자의 실제 도구 성능을 단정할 수 없습니다.

### 3. 정확한 파일을 알아도 손실이 남습니다

정답 파일을 미리 지정한 **불공정한 진단용** 영어 검색에서:

- `s5`, `s6`: 필수 근거가 후보에는 모두 있었지만 기본 최종 반환에는 하나도 남지 않았습니다. 발견과 선택의 손실이 구분됩니다.
- `b4`: 후보에는 전부 있었으나 최종 반환에는 3개 중 2개만 남았습니다.
- `b1`: `runtime.ts`를 직접 지정해도 파일을 읽은 뒤 후보 대상에서 제외했습니다. 현재 자격 증명 패턴이 공개 코드의 URL 비밀번호 **가림 표시를 대입하는 문장**(`runtime.ts:148`, `redactUrlToken`)에도 일치했습니다. 파일 전체를 제외하는 보수적 필터의 오탐입니다. 실제 비밀번호를 보고서에 기록하지 않았습니다.

보안 필터를 단순히 끄거나 실제 민감 자료를 보내는 우회는 해결책으로 취급하지 않습니다. 별도의 안전한 오탐 회귀 검증이 필요합니다.

## 시간 해석

한국어 scan/render 중앙값은 생성 순서별 약 **98/108ms**, 영어는 **6/7ms**였습니다. 영어가 빨랐던 것은 초기에 후보 12개를 채우고 멈췄기 때문입니다. **작업을 더 빨리 해결했다는 의미가 아닙니다.** 이미 파일을 검증·복사한 warm-cache 조건이며 주 모델, 승인, 인증, 네트워크, 정답 작성 시간은 포함하지 않습니다.

## 다음 단계와 중단 조건

1. 유료 정렬 실행은 아직 진행하지 않습니다. 현 후보의 정답 근거 상한이 너무 낮습니다.
2. 먼저 조기 탐색 종료와 후보 선택을 제한된 범위에서 개선하거나, 실제 부모가 생성하는 검색어·경로를 독립 세션에서 관찰해 이 강제 입력 실험과의 차이를 확인해야 합니다. 제품 수정과 추가 모델 실행은 이번 결과에 근거해 별도로 결정합니다.
3. 이 10문항으로 조정했다면 이를 학습/개발 세트로 취급하고, 새로 동결한 보류 문항으로 다시 검증해야 합니다.
4. 그 뒤 동일 주 모델의 A(기존 도구)/B(로컬 도구)/C(Jev 도구)를 비교합니다. C와 추가 모델 실행은 모델·전송 데이터·호출 수·최대 비용을 먼저 정해야 합니다.

자연 선택, 정답률, 추가 읽기 횟수, 전체 작업 시간·비용은 여전히 미측정입니다. 합성 회귀 통과나 이 로컬 검사만으로 기본 설치를 바꾸지 않습니다.
